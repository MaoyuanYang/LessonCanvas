## Architecture Placement

- New backend module `apps/backend/src/lessoncanvas/modules/product_validation/` (Alignment-and-Evaluation ownership, same pattern as F009's `technical_evaluation`): `rubric.py` (fixed `rubric-r1` definition — five dimensions, four severe classes, structural-rework rule, attestation fields, thresholds; a pure validation function returning every violation; zh-Hans printable-sheet data), `service.py` (assignment fixing, evidence import, deterministic outcome computation, overall-status derivation, staleness derivation, overview/detail reads), `schemas.py`. Zero model-adapter calls anywhere; no Celery task (synchronous imports and deterministic computation bounded by rubric size).
- Package identity: at assignment creation the service reads the unit's current-of-record artifact set through the existing alignment/artifact reads, records per-lesson (lesson_index, family, artifact_id, checksum) triples plus the confirmed brief/blueprint version ids and dataset revision, and derives a `package_digest` (SHA-256 over the sorted identity tuple). Assignment uniqueness/enabled idempotency on (project_id, unit_key, package_digest). Staleness is a read-side derivation: an assignment is stale when a newer confirmed pair exists for that unit lineage, or the current-of-record artifact set for the bound pair no longer matches the recorded identity; stale never mutates stored outcomes (Spec D5).
- Evidence import: single transaction — validate payload against `rubric.py` (all violations returned at once), store the uploaded original document through the existing object-storage helper under a workspace-private prefix (bounded size/type per existing upload conventions; filename stored as untrusted metadata), persist the evidence row with `capture_channel = owner_mediated_import`, and compute the unit outcome in the same commit. Uniqueness on (assignment_id, rubric_revision) gives idempotency; a new revision supersedes the prior row (prior flips `superseded`, outcome recomputed only from the current revision; terminal rows immutable).
- Overall status per project: read-side derivation over assignments per Spec D6 precedence (not_evaluated -> failed-definitive -> not_complete -> in_progress -> passed); per-unit `not_complete` recorded with a reason when an assignment is concluded without complete evidence.
- New router `api/product_validation.py` (`/projects/{id}/product-validation...`), registered in `main.py`; ownership via the existing `WorkspaceDep` + `get_owned_project` pattern; errors via `api/errors.py` (requirement classes list every violating field).
- Shared-surface change: `alignment_evaluation/service.py` `PRODUCT_VALIDATION_STATUS` constant and `technical_evaluation/service.py` report constant are replaced by a call into `product_validation.service` overall-status derivation (field name `product_validation_status` unchanged in all three reads: alignment, technical-evaluation report, delivery report snapshot); the F009 report independence note drops the "until F010" clause. F008/F009 consumers see a value-vocabulary extension only.
- Migration `f010...`: additive tables `product_validation_assignments` (id, project_id FK cascade, workspace_id, unit_key, dataset_revision, brief_version_id, blueprint_version_id, package_json, package_digest, rubric_revision, state, not_complete_reason, created_at/updated_at/concluded_at; uq (project_id, unit_key, package_digest)) and `product_validation_evidence` (id, assignment_id FK cascade, rubric_revision, evidence_json, capture_channel, document_object_key/filename/checksum, outcome, outcome_reasons_json, status current|superseded, superseded_by_evidence_id, created_at; uq (assignment_id, rubric_revision)). Audit via the existing `audit_events` pattern; deletion cascades from `projects` cover both tables and storage cleanup follows the existing project-deletion object sweep.
- Web: typed client additions + product-validation status label map in `lib/api.ts`; new `components/product-validation-region.tsx` rendered in `evidence-panel.tsx` below the 技术评估 region (create modal, inline import form with full-violation display, expandable detail with evidence-revision history, stale guidance); `alignment-panel.tsx` second status chip becomes live; `technical-evaluation-report-view.tsx` and `print-report-view.tsx` status lines become live; rubric hand-out sheet renders from assignment detail (print-styled, zh-Hans). No new tokens, tabs, or visual language.
